03

一次「提交订单」经过谁

这是全项目最重的一条链路：跨档口拆单、金额重算、快照、清车，五件事在同一个事务里完成。

01
CheckoutPage

校验地址非空（≥ 5 字）。不合法就直接返回，不发请求 —— 这就是「地址为空不建单」的第一道防线。

02
api/client.ts

拼 POST /api/orders，带上 Bearer token。请求体里只有 address 与 remark，没有任何金额字段。

03
routes/orders.ts

取出字符串、调用 createOrders()。这一层不做判断，只搬运。

04
domain/orderService

读购物车（join 菜品与档口）→ 空车拒绝 → 再校验一次可售状态（加购后可能被置为售罄）→ 按 stall_id 分组。

05
domain/pricing

每组算 Σ(单价×数量)；满 ¥20 免配送费，否则 ¥1.00。金额全程整数「分」。

06
db · 事务内

每组写 orders + order_items（菜名与单价快照）+ 一条 order_status_logs（null → paid），最后按菜品删除购物车条目。任一步失败整体回滚。

07
CartContext

用响应里的新购物车整体替换本地状态（不做本地累加），顶栏计数立刻归零。

08
CheckoutPage

渲染结果页：几笔订单、各自订单号与可取消提示。

04

订单状态：只有一条路可走

状态不是「存了一个字段然后到处改」，而是由 statusMachine.ts 的白名单 + 时间阈值共同决定。没有人能直接把状态写成「已完成」。

paid 已支付 +25s → preparing 备餐中 +75s → ready 待取餐 +180s → completed 已完成
paid 已支付 25 秒内取消 → cancelled 已取消 超时取消 → 409 CANCEL_WINDOW_CLOSED

怎么推进

读订单时先 syncStatus()：逐级判断是否到点，到了就写一行日志。逐级推进天然不可跳步。

为什么不用定时器

没有后台任务，进程重启不丢状态；时间由 paid_at 推导，测试可以直接改写时间做验证。

谁能改状态

只有两处：syncStatus（按时间）与 cancelOrder（用户取消），都过同一个白名单校验。

05

数据怎么摆

七张表。关键设计是 order_items 冗余菜名与单价——订单一旦生成，就不再受菜品改价影响。

表关键字段和谁有关
usersstudent_no（唯一）登录即建档；一个学生一份购物车、多笔订单
sessionstoken每个 token 指向一个用户，登出就删行
stallsis_open、prep_minutes一个档口多道菜；订单的配送费与出餐时间以档口为单位
dishesprice_cents、statuson_sale / sold_out / off_shelf 三态决定能否加购
cart_items(user_id, dish_id) 唯一只存「谁要几份」；金额每次读时现算，不落库
ordersstall_id、total_cents、cancel_deadline一单一个档口；跨店下单会产生多行
order_itemsname_snapshot、price_cents_snapshot快照：菜改名改价都不影响历史订单
06

金额只有一个算法，且不在浏览器里

加购时

不算钱，只算份数

购物车只存 qty。前端显示的金额来自接口每次现算的结果。

提交时

服务端重算

按 dishes.price_cents × qty 求和，再按档口加配送费。totalCents 若出现在请求体里会被直接忽略。

展示时

只做格式化

yuan(cents) 是唯一的展示入口，避免各页面各写一套四舍五入。
